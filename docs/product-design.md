# Product design system

Status: authoritative product design rules for the current clients and server UI. Audience: product and client contributors. This is the single design authority; component theme files implement these rules and do not establish competing systems. Runtime acceptance is platform-specific; these principles do not certify untested devices or service integrations.

## Identity and hierarchy

DIDMail is simple, calm and trustworthy. Black, white and gray establish order; functional color communicates meaning. Proportion, alignment, whitespace and restrained light establish depth. The original white peace dove conveys protection and warmth. Preserve its paths, aspect ratio, opacity and identifying details; a generic mail icon is not a replacement for the mark.

Every visual choice serves clarity, usability and trust. Brand entrances may use soft neutral light and restrained neutral gradients. Mail lists, reading and composing favor stable, low-noise surfaces. Avoid decorative colored blocks, colored halos, terminal and neon associations. Do not grayscale authored mail, namecards, photographs, attachments or original brand assets.

The original transparent white artwork is [the mobile SVG](https://github.com/didmail-org/mobile/blob/main/src/assets/images/logo.svg); the extension includes a byte-identical [browser copy](https://github.com/didmail-org/extension/blob/main/public/images/dove.svg). Small navigation marks and system application icons retain their existing purpose and original geometry. Large brand scenes use the transparent original directly in full-page black space; never reuse an application-icon tile as hero artwork. Never redraw, invert or recolor the source artwork to fake contrast.

Flutter retains the original SVG and renders the brand with a faithful [transparent bitmap export](https://github.com/didmail-org/desktop/blob/main/assets/brand/didmail-dove.png). This preserves authored white/dark detail and avoids reliance on SVG CSS/color-filter behavior in the native brand renderer. Preserve the source view box, aspect ratio, authored ink and transparency when regenerating it. Keep authored mail and template rendering in their existing content renderers.

Use one dominant action per task area. Compose is the primary mailbox action; folders stay together. In extension navigation, keep Compose easy to find by position and icon, but apply the same route-specific selection treatment as other destinations: only the current route is highlighted. Do not leave Compose permanently filled or elevated while a folder is active. Contacts are a destination, while server connections and account management are supporting destinations. Preserve existing routes and deep links. Put payment and recovery details where they inform a decision, and retain all required consent and irreversible-action confirmations.

## Appearance and semantic roles

Both appearances are first-class. Light uses a pale gray environment and soft white work surfaces. Dark uses near-black, charcoal and gray to establish depth. Primary actions, selection, focus and hover use luminance contrast, weight, shape and icons. Color requires a named functional purpose: error/destructive risk, warning/pending attention, verified success or useful identification. Each status also has text, an icon or a shape. Brand scenes (the server hero and actual client launch, welcome, account-loading and sign-in pages) use a full black or near-black neutral background in both preferences. Their text, controls and native bars use readable light foregrounds. This local presentation rule neither creates a third theme nor writes the saved preference. Functional pages resume the selected Light/Dark palette.

| Semantic role | Light anchor | Dark anchor | Intended use |
| --- | --- | --- | --- |
| Environment | `#F2F2F2` | `#111111` | Canvas around the task; the lowest layer |
| Navigation | `#E9E9E9` | `#181818` | Folders, grouped tools and supporting regions |
| Workspace | `#FAFAFA` | `#1C1C1C` | Mail list, account forms and editing |
| Reading | `#FAFAFA` | `#171717` | Quiet default document canvas; native renderers may use workspace |
| Floating surface | `#FFFFFF` | `#292929` | Menus, pickers and dialogs above the task |
| Main text | `#202020` | `#F5F5F5` | Main task text and headings |
| Supporting text | Around `#606060` | Around `#BDBDBD` | Readable metadata, descriptions and labels |
| Primary intent | `#292929`, white foreground | `#EDEDED`, dark foreground | Main action; other states use neutral contrast and shape |
| Selection / hover | `#E3E3E3` | `#343434` | Current-item semantics, weight or icon accompany selection |
| Structural boundary | Around `#D4D4D4` | Around `#414141` | Quiet separation of groups and rows |
| Control boundary | Around `#8C8C8C` | Around `#858585` | Required input and control affordances |
| Focus | `#404040` | `#E0E0E0` | Clearly visible 2px outline with offset |

Surface order describes function, not an instruction to make every region a brighter card. Navigation and workspace may share a dark fill when a boundary and layout clearly separate them; floating content must remain distinguishable. A scrim is a separate translucent background for modality, never a readable surface. Organize ordinary content with whitespace, alignment, headings, weight and surface tone. Remove repeated page–panel–card–inner-box boundaries that perform the same job. Keep necessary input, table, panel and resize boundaries, and list dividers that help reading. Never clear borders or outlines globally, or replace each removed border with a shadow. Ordinary task regions stay flat; neutral gradients and edge highlights only explain actual depth. These are semantic anchors, not a requirement for identical hex values in native renderers. Verify normal text at 4.5:1, large text and required control boundaries at 3:1, and visible focus separately. Never use low-opacity supporting text as a substitute for a readable token.

Provide exactly **Light** and **Dark**. Each main shell and sign-in entrance exposes a one-action toggle in the existing header or toolbar. Its icon, tooltip and accessible name describe the target, such as “Switch to dark”. Do not require a menu or multiple settings levels. Apply immediately and persist; preserve drafts, selection, navigation and open tasks during a switch.

Preserve existing explicit light/dark preferences. Migrate legacy explicit `system`/`auto` once: capture the currently effective palette already applied by the old shell, or sample platform brightness once if no valid applied value exists, then save fixed light/dark before interactive rendering. No operating-system color listener remains after resolution; later system color changes never change the app. Preserve any existing fixed product default; these implementations previously defaulted to system appearance, so genuinely new installations and invalid preferences use **Dark**. If an old release represented System only by a missing value, it is indistinguishable from a new installation without existing installation metadata; record that compatibility limit rather than claiming exact migration.

Resolve appearance before visible content when possible. Keep menus, dialogs, editor chrome, toasts and native status/navigation bars consistent. Retain existing cross-tab synchronization. When storage fails, retain session choice and existing safe fallback storage without clearing unrelated data; do not claim persistence if all stores fail. Server no-JavaScript fallback is fixed dark. System font scaling, screen readers and reduced-motion behavior remain independent and supported.

A static night launch with the original white dove gives native clients a consistent starting surface while preferences resolve. Keep brand frames black while resolving the preference; apply the restored palette when entering functional pages. Inspect native launch resources as well as Dart/JavaScript startup; a correctly themed application frame alone cannot establish early-frame flash behavior.

Keep roles in each client's existing theme system; do not add a shared runtime just to share styles. Browser startup must obey extension CSP. The server retains its native framework-free ARC/AUP header and preference contract. Desktop mail favors efficient panes; touch clients favor reachable controls, keyboard clearance and clear return paths. Narrow extension windows retain list context when switching to the reader.

Rich mail is an authored document, not application chrome. Do not blanket-invert HTML, images or attachments. Preserve existing content security, remote-media restrictions and authored colors. Where the renderer cannot safely combine arbitrary authored backgrounds with dark defaults, use a clearly bounded neutral document canvas inside dark chrome and verify both light-authored and dark-authored examples. Plain/default content should use native theme colors.

## Typography, spacing and interaction

Use the installed platform/system sans stack with its CJK fallbacks. Do not download a proprietary reference font or force a desktop font onto a native client. CSS sizes below use a 16px root and must scale with user preferences; native roles preserve comparable hierarchy through their existing text themes.

| Role | Extension/web default size / line height | Weight | Use |
| --- | --- | --- | --- |
| Task title | 20 / 28px | 600 | Account, contacts and task headings |
| Section heading | 16 / 24px | 600 | Form groups and reader sections |
| Workspace body | 14 / 21px | 400 | Rows, form values, navigation and supporting prose |
| Label / action | 14 / 20px | 500 | Field labels and button text |
| Reading body | 16 / 26px | 400 | Default mail document; authored content retains its own styling |
| Metadata | 12–13 / 18–20px | 400 | Dates, status and supporting information; never the only place for a critical warning |
| Identity / address | 12–14 / 20–22px | 400 | Complete DID or technical identifier with optional system monospace |
| Welcome name | 24–32 / 32–40px | 600 | Centered product identity below the large dove in brand entrances |

React Native may retain its 24/32 title, 18/26 heading, 15/23 body and 13/20 caption. Flutter retains Material text roles with 26px brand/page emphasis, 22px titles, 16/14px body and 12px metadata. Server admin may retain its 24px page heading. These are deliberate platform adaptations, not additional design authorities. Do not reduce type to compensate for a narrow layout or suppress native text scaling.

The extension's compact mail list uses a 15px/20px subject, medium for read mail and semibold for unread/selected mail, with 11px/16px address and timestamp metadata. Date and local time occupy two short lines in the trailing column beside the subject/address group, so time does not add a new row. Use locale-aware date/time formatting and expose the complete timestamp to assistive technology and on hover. Compact pointer copy controls may be 24px; coarse-pointer hit areas remain at least 44px. Other identity displays keep their larger defaults.

Use the extension workspace header as the single page title, with 14px narrow and 16px desktop supporting-page roles. Do not repeat a visible title above mailbox filters or above contact/server/account content already named in that header. Searchable mail routes may keep the desktop heading screen-reader-only because the selected navigation item provides visible context. Preserve meaningful section headings and dialog titles.


Use a small, coherent text hierarchy: page/task heading, section heading, body and supporting text. Prefer regular body text, medium labels and semibold headings; reserve heavier weight for rare brand emphasis. Native long-form prose may use roughly 60–76 Latin characters per line; extension mail reading and composing instead use the full available pane width without a fixed prose cap. Preserve appropriate CJK line breaking, clear paragraph rhythm and tabular numerals for quantities. Inspect heading orphans, button wrapping and icon optical alignment with actual localized text, rather than shrinking every font. Addresses and IDs may use monospace; they must wrap, truncate deliberately or expose a complete copy action without forcing the viewport wider.

Base spacing on a four-point rhythm: 4px for icon/text association, 8px within a control group, 12px between related controls, 16px within a task region, 24px between form groups and 32px between major sections. Desktop page gutters are 24px, reducing to 16px in narrow windows. Use approximately 8px control radius, 12px panels and 16px large dialogs; native 10px controls and existing 12/16px Material shapes are equivalent adaptations. Reserve full pills for small status chips or actual segmented controls. Use a 1px structural line and a clearly visible 2px focus treatment; do not rely on a decorative hairline for an input boundary. Match corner radius, border and shadow to component size. Use surfaces to organize regions; do not wrap everything in decorative cards. Soft elevation signals genuine floating layers such as menus and dialogs; focus uses a visible outline. Brand entrances can be more expressive; text-bearing task surfaces stay calm. Touch controls should offer at least 44 logical points; pointer interfaces must also retain clearly visible focus and usable targets. Follow the native platform's larger minimum where applicable.

Forms retain entered content after recoverable failure, expose validation beside the relevant field, prevent duplicate submission and communicate busy/disabled states. Cancelling a dialog returns focus to its trigger. Leaving an unsent composition requires a clear discard decision where supported, without persisting plaintext into a new storage mechanism. Account locks and switches retain their existing security boundary.

Mail lists must scroll independently without hiding filters or primary actions. Readers handle long subjects, addresses, bodies and attachments. Temporary layers stay inside the viewport, remain scrollable when necessary and support keyboard dismissal. Safe areas and keyboards must not cover native form actions.

Loading, an empty folder, no search results, offline access and failures are different states. Use task language and an actionable recovery where one exists. Do not display an unavailable balance as a verified zero or describe uncertain delivery as unpaid. Preserve exact fees, retention terms, recovery warnings and authorization semantics.

Use short, lightweight feedback for press/release, expansion, panel transitions and completion. Prefer opacity/transform and avoid layout work during scrolling/input. Honor reduced-motion preferences across CSS and native animations. No continuously looping logo flight, pulsing text or attention-seeking background effects belong in reading or composing.

## Content and layout behavior

Use language-aware wrapping. Set the correct document language, use normal CJK line breaking and avoid negative letter spacing on Chinese text. Permit punctuation-aware wrapping; do not force every Chinese label onto one line or add manual breaks to fit a single screenshot. Long headings wrap into natural lines without hiding the full subject in the reader. A list row may truncate a subject or preview deliberately, with the full title available when opened.

An identity row gives the DID the remaining width with `min-width: 0`, flexible text and nonshrinking copy/QR controls. Use normal word breaking plus `overflow-wrap: anywhere` for opaque IDs, URLs and attachment names. Isolate identifiers left-to-right inside RTL chrome. If controls leave too little room, move them to a second row before an address becomes a single-character column. Account identity displays the complete DID where space permits; a narrow native summary may truncate deliberately when a clearly labeled detail/QR view exposes the selectable full value. Copy always uses the exact original DID and provides feedback; an unavailable value has an explicit placeholder, never the strings `undefined` or `null`.

Button labels describe an action with a short verb and object when needed. Preserve all localized words, keep icons at a stable size and wrap/stack an action group before compressing text. Avoid vertical letter stacks and clipped labels. Dense pointer controls are generally 32–36px high and standard extension buttons are 40px high; coarse-pointer controls need at least 44px hit areas and Flutter follows its 48px minimum. Use auto height when translated text or text scaling needs more room. Disabled/busy controls retain understandable labels and a nearby reason where the cause is not evident.

## State and feedback contract

| State | Required representation and recovery |
| --- | --- |
| Loading | Identify the task being loaded; use a stable placeholder or restrained progress indicator without inventing a balance, delivery result or count. Keep existing local content when refresh can run separately. Announce meaningful progress without flooding live regions. |
| Unknown / unavailable | Show an em dash with an accessible explanation or localized “Not provided” / “Unavailable”. Missing service terms, stake and balance remain unknown; never coerce them to zero, unpaid, unlimited or successful. |
| Failure | Explain the failed task beside its content, retain entered text and existing valid selections, and offer a scoped retry where supported. Technical diagnostics can be expandable. Failure must not look like an empty successful result. |
| Empty data | Name the empty folder or collection and an available next action. Distinguish an empty mailbox from no search matches; the latter offers changing/clearing the query. |
| Disabled / busy | Use native disabled semantics and prevent duplicate actions. Preserve a readable label, indicate active work and expose the unmet condition when useful. Visual opacity alone is insufficient feedback. |
| Success / selection | Confirm completion or selection in text as well as color; copy feedback must be perceivable. Keep focus and selection stable after refresh. Do not announce security or delivery guarantees beyond verified application state. |

Workspace motion is brief feedback: about 120–180ms for color/opacity and at most 200ms for a small panel transition. Stable text and controls take priority; avoid `transition: all` on task geometry. Honor reduced motion and do not animate row height, large gradients or a breathing logo while reading/composing. Only welcome artwork follows the richer timeline below.

Mailbox synchronization failures default to a single short, localized status beside Retry. One native disclosure reveals the original scoped failure, cached-mail/new-mail impact and diagnostics; do not delete or weaken those details when shortening the initial presentation. Bound the expanded detail area and allow it to scroll so filters and mail remain reachable. Keep loading, disconnected, local-read failure and successful completion distinct.

## Welcome motion

Use existing welcome, authentication-loading and sign-in entries; never add a timed splash or delay authenticated navigation to finish an animation. Large brand scenes use an uninterrupted black or near-black neutral background even when Light is selected. The server hero spans the viewport width and at least a full first-screen region with a coordinated dark native header. Client entrances use the entire page, with no white surround, rounded scene card or contained black tile. Preserve the two-theme preference and restore its functional surfaces on exit. Entrance headers avoid repeating the main product wordmark: the extension keeps utility actions only, native entrances keep existing navigation/utility actions, and the server retains its accessible small home link without a second visible title. The product name stays with the main dove. Authentication fields and account selectors, and the server’s own form fields, indicate focus by increasing neutral border luminance while retaining the original stroke width and font weight, without additional rings or shadows. Keep a visible system focus outline in forced-colors mode.

Use the original transparent dove directly in this space, preserving its full wings, letter, shield/heart meaning, geometry, source files and aspect ratio. Inspect baked image backgrounds, container fills, clipping, borders, shadows and gradients before changing assets. Remove large carriers, discs, badge outlines, circular masks and local halos. Do not simulate wing motion by distorting the artwork or create a glow outline with drop shadows. Static navigation marks and platform app icons retain their separate small-scale purpose.

Measure the visible artwork rather than its transparent image box. Start around **320–480 CSS pixels of visible width on desktop** and **180–260 logical pixels on narrow screens**, then adjust to real available height, safe areas, font scaling and operations. Center the spacious dove above the name and short description. On wide brand entrances (around 1024 CSS/logical pixels, adapted to usable native width and font scaling), place the dove/name/description group in the left column and the existing registration/sign-in form in the right. On the server public home, the right column contains the existing introduction and entry actions; do not invent a form. Standalone launch/readiness surfaces may retain one centered composition. Account-loading placeholders inside an authentication entrance retain its responsive composition so that resolving the form does not shift the dove. Narrow windows retain a single vertical flow. Divide the full page width into equal halves and center the visible brand and form groups horizontally and vertically within their half, rather than centering a limited-width grid inside the page. A stationary 1px neutral vertical separator on the page midpoint is brightest at its center and smoothly fades to transparency at its top/bottom ends; hide it in the narrow single-column layout. Keep the form fields left-aligned within the centered form group. Short windows and oversized forms scroll normally, preserving access to the complete content. Reserve the full movement envelope above and around it. Short windows, larger fonts and keyboards scroll naturally; do not shrink the mark back to a small application icon to fit the first screen. Keep inputs and actions reachable and stable.

The dove enters uniformly from scale **0.76** (acceptable range 0.72–0.8) and soft opacity to its resting pose over about **1.8 seconds** (1.4–2 seconds), with natural deceleration and no bounce or rotation. Continue without a pose jump into a **12-second** (10–16 seconds) smooth loop from scale **1 → 1.10 → 1**, with a gentle **24 logical pixel** upward return float (16–28 where space permits). Both ends have zero velocity. Product names, explanatory text, inputs and buttons remain stationary. Only the dove and separate environmental layers move.

Environmental light belongs to the page, independent of the dove. Broad diagonal diffusion from an edge or soft cross-page gray-white bands may move over about **24 seconds** (18–30 seconds). Their extent is clearly larger than the artwork, asymmetrical and fully dissipated, with no clear circle, spotlight or glow badge. Keep a stable black base, clear white feather detail and readable text. Move/adjust opacity of existing layers rather than continuously repainting large animated blurs. Static light is also valid on native platforms.

Animation never gates loading or interaction. Theme switches, typing, ordinary rebuilds and foreground restoration preserve the timeline without another entrance. Pause the ongoing timeline while hidden, covered, offscreen or backgrounded; resume its phase when visible. Release listeners, observers and controllers on disposal. Native system launches remain static and follow each platform's launch mechanism; hand off promptly into the app without a mandatory wait.

Read reduced motion before starting. Initial reduced motion shows the complete, static composition. A live change settles at the visible resting pose and consumes the entrance; disabling it later may resume the loop without another entrance. Failed animation enhancement leaves the dove visible. Keep extension CSP and the server's framework-free ARC/AUP runtime; no additional animation library is needed.

Acceptance requires real-time playback of at least one whole dove cycle, not screenshots or timeline seeking alone. Capture matching Light/Dark screenshots and complete-cycle recordings where feasible. Exercise small/short windows, larger text, keyboard and input, theme preservation after exit, initial/live reduced motion and offscreen/route/background pause/resume. Check the actual visible bounds at rest and peak for clipping or collisions. Record whether evidence comes from a browser, native desktop, simulator or device, and whether lifecycle events were real or simulated. Keep unsupported/unavailable targets explicit; source code, widget tests and builds do not prove actual native playback.

## Iteration and evidence

For each change, record the affected entry, user task, important states, severity and current validation method. Begin with real interface observation and a page/theme/state coverage table. Revise this specification, then tokens/shared controls, verify representative login, inbox/reader, compose and account tasks, and propagate to every existing route. Each round follows observed issue → user impact → implementation → runtime → screenshot review → operation regression. Independently recheck screenshots and operations, preserving validated designs instead of changing style to meet an iteration count. Recheck consumers of shared components, nearby window sizes, long content, both supported themes and relevant locales including RTL.

Use synthetic/offline data in isolated profiles or disposable native fixtures. Never send external mail or broadcast chain transactions from UI checks. Keep screenshots, per-run coverage tables, command logs and checkpoints under the ignored root `artifacts/` directory. Do not commit real mail, credentials, databases or device state. Match window size, zoom, language, theme and data in before/after comparisons.

Run [component validation](../CONTRIBUTING.md) and distinguish static checks, browser rendering, simulator rendering and device acceptance. For the extension, `node scripts/ui-workspace.browser.test.mjs` from the `extension/` repository root exercises the built unpacked export with public test identity and offline mail fixtures. Build it first with `pnpm build:dev`. The theme regression (`pnpm test:theme` after a build) additionally checks persistence, fixed default, legacy-system migration, OS changes having no effect, cross-tab changes, pre-hydration appearance and paired rendered states. Record unavailable platforms and unexercised service states explicitly; a passing build cannot replace visual or interaction acceptance.

Acceptance evidence must include the checked-out source/build relationship, Chrome version and unpacked path, screenshot pairs with identical viewport, device scale, zoom, locale, synthetic data and settled animation phase, plus interaction assertions. Hash the assets Chrome actually loads and compare them with the current export; merely finding an output directory or an installed extension name is insufficient. Record the pre-edit working-tree baseline separately so existing valid work is not misrepresented as this iteration's changes.

Verify legacy-system migration under both effective appearances, fixed default dark, explicit preferences, persistence/reopen, storage failure and later OS color changes having no effect. Inspect first paint, open menus/dialogs/editor and applicable native bars; record launch limitations separately. For the representative pages, inspect both themes and explicitly exercise full DID display/copy, long localized subjects, a smaller window, unavailable data, recoverable failure, empty/no-result lists and primary actions. Observe one complete welcome entrance/float cycle and live reduced-motion change; still screenshots cannot establish playback. For every additional platform/page, state whether evidence is static analysis, automated rendering, simulator or device interaction. Keep unavailable native platforms and unexercised integrations as named validation limits rather than inferred passes. Screenshots and run reports belong in ignored artifacts, not this maintained specification.
